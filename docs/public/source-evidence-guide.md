# Read source evidence

Start with the authoring problem: identify the affected record and field, open
its owning editor, and review the proposed change. Technical evidence helps
explain an unusual imported value or a compatibility warning. It does not
replace the authoring controls or establish a playable route by itself.

In Issues, retain the exact finding's identity when opening its editor or
technical details. A missing or ambiguous target must be resolved deliberately;
a similarly named record is not an automatic replacement. Use the Source Evidence
surface from the Issues context when you need the retained native information.

## Distinguish the kinds of evidence

| Evidence | What it can establish | What it does not establish |
| --- | --- | --- |
| Retained native bytes | What was present in the imported files, including padding, tails and unavailable records. | That every byte represented intentional authored content or safe executable behavior. |
| Source analysis | How a pinned original reader or writer handles a particular field or instruction. | That the same path was independently observed in a running Classic game. |
| Executable fixture | A named behavior, boundary or preservation rule passes a reproducible check. | Every possible scenario or every variation of the mechanic. |
| Build or package verification | The tested source builds, or the exact archive validates against its stated contract. | That a player can reach an encounter or complete a campaign. |
| Native authoring journey | The exercised controls, history, persistence and exports work for the recorded task. | Runtime parity for unplayed events. |
| Calculated path | A route was found under the supplied movement rules and state. | Discovery, encounter eligibility, unchanged state along the route, or permanent unreachability when no path was found. |
| Runtime traversal | The recorded starting state and sequence reached the recorded ending state. | Guaranteed success for every party, seed or untested branch. |

An isolated fixture, prepared checkpoint, direct program invocation or debug warp
must remain labelled as prepared evidence. Auto Win can establish an observed
battle aftermath under a winnability assumption; it does not supply money, items
or access that the party did not have.

## Use identities to keep comparisons honest

Record identities distinguish native records even when names repeat. Input and
artifact fingerprints distinguish source sets, binaries and packages. They
identify evidence; they do not grant or deny permission to import a third-party
scenario.

A historical receipt remains attributed to its original source and build.
Updating an application library, package schema or runtime does not turn that
receipt into verification of the new pair. A useful report names the tested
scope, observed outcome, remaining uncertainty and next owning-editor action.

## Preserve the original while repairing

An imported project can retain content that current runtime output cannot safely
use. Read the warning's source and consumption conditions before deciding what
to change. Keep an original copy of a scenario outside the editable project.
Review shared settings before applying: changing one caller must not silently
alter other callers.

When an operation's result is uncertain, follow its comparison or status-check
path. Checking an outcome must not apply or retry the change. Keep any copied
draft until the editor establishes what happened.
